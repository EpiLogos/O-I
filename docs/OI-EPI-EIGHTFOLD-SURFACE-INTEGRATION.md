# O:I Desktop Integration — Epi Eightfold Product Field

Status: application-integration design under `docs/positions/FOUNDING-POSITIONS.md` and `docs/OI-DESKTOP-APPLICATION-SPEC.md`.

Epi semantic/product authority remains in `EpiLogos/Epi-Logos-C-Experiments`, currently developed in design PR #19:

- `Idea/Bimba/Seeds/M/EPI-EIGHTFOLD-EXPERIENTIAL-VISION.md`
- `Idea/Bimba/Seeds/M/EPI-EIGHTFOLD-APPLICATION-ARCHITECTURE.md`

This O:I document does **not** redefine the M/M′ system. It states how the current composable desktop hosts it.

---

## 1. The host now accounts an eightfold Epi product field

The Epi application exposes eight product-scale experiences from six semantic M′ domains:

```text
PARENT 3:3 PRODUCTS
  epi.cosmic.123
  epi.personal.450

DEEP 4+2 PRODUCTS
  epi.deep.m0
  epi.deep.m1
  epi.deep.m2
  epi.deep.m3
  epi.deep.m4
  epi.deep.m5
```

The eightfold is not eight new O:I products and not eight M coordinates.

It is an Epi-owned application ontology that O:I hosts through native Surface/Application contracts.

The distinction matters to the desktop because the parent products and deep products have different interaction densities while sharing semantic identity:

- a parent product is a whole current lived/cosmic composition;
- a deep product expands one M′ domain into its bespoke recursive 4+2 instrument;
- opening depth must not require a second shell or a duplicate semantic event.

## 2. Application state remains three-layered

The current desktop law remains binding:

```text
EPI SEMANTIC / CURRENT STATE
    eventRef / protected subject
    M refs / source / DAY-NOW / provider lineage / readiness

WORKBENCH CONTEXT
    SessionSpaceRef
    AgentSessionRef
    selected subject
    effective Context / available Surfaces

PRESENTATION
    Cosmic | Personal face
    parent | deep product
    tab / split / focus / camera / renderer mode
```

The eightfold adds product identity to the presentation/application layer without collapsing that identity into the semantic event.

`epi.cosmic.123` and `epi.personal.450` may both project the same current event. `epi.deep.m2` may open from that same event. None of those presentation changes mints a new event merely because the user changed scale.

## 3. Parent Personal product — ordinary workbench activities are the point

The Personal 4/5/0 product is not required to look like a continuously mounted deep Nara psychoid renderer.

It should be able to compose the ordinary lived activities that matter:

```text
journal / writing
DAY / NOW canvas or dashboard
kanban / flow / activity organization
note / episode work
oracle / reading
canonical Epii dialogue
Explain / History / provenance
Bimba/source/canon reveal
proposal / recognised return
```

These activities may use different native Surface bodies while remaining one Personal product over one governed subject.

### Current desktop disposition

```text
Nara writing/day/flow/oracle
    CANVAS, NAVIGATOR, COMMAND as current native contracts require

Epii canonical dialogue
    SIDECAR through Actuation + AIKit AgentSession

Epii summoned pedagogy / Logos reading
    CANVAS | SIDECAR-linked | ALTERNATE-NATIVE

Bimba / source / coordinate ground
    NAVIGATOR + KNOWLEDGE + CANVAS + COMMAND

Explain / History / provenance
    INSPECTOR / SIDECAR; Canvas only for richer reading

proposal / return
    COMMAND + Inspector/Canvas result through native Central authority
```

The full protected psychoid/quaternion/chakra organism belongs primarily to `epi.deep.m4`. The parent may expose bounded current-state indicators or a deep-open affordance without making the deep renderer permanent chrome.

This corrects the previous temptation to make all of Nara's internal M4 dynamics one always-open Canvas composition.

## 4. Parent Cosmic product — one current world, not three mini instruments

`epi.cosmic.123` is one Epi Canvas contribution over one current event.

It receives Epi-owned current M1/M2/M3 contributions and may use a rich native body, but it must remain a parent-scale composition rather than the full deep M1′ + M2′ + M3′ tools mounted simultaneously.

Current design direction from the Epi source:

```text
M1
    compact current QL/topological act

M2
    live solar / harmonic / correspondential world-condition

M3
    current clock / inscription / symbolic state
```

The desktop must not reconstruct those semantics. It mounts the effective Epi body and exposes the same refs/Actions to human and Agent.

A displayed planet/relation/state glyph must therefore resolve to a native Epi ref. Clicking it can update workbench selection, open Inspector/Knowledge, invoke a canonical Action, or open the relevant deep M′ product without DOM-derived semantics.

## 5. Six deep products — ordinary Canvas application operations

Each deep M′ instrument is a first-class native Surface family:

```text
epi.deep.m0  Bimba / language / graph / relation world
epi.deep.m1  played K² / Ananda / QL instrument
epi.deep.m2  72-space / harmonic / cymatic / frequency instrument
epi.deep.m3  symbolic-genetic 360/720 clock/transcription instrument
epi.deep.m4  protected Nara psychoid / body / trajectory instrument
epi.deep.m5  Epii pedagogical / canon / developer / Logos instrument
```

They open through the **same generic workbench presentation machinery** as other Surfaces:

- current/new tab;
- split;
- focus;
- restore where the provider supports it;
- alternate native body when React/DOM is not the right substrate.

No `EpiDeepShell`, `MPrimeDesktop`, or special deep-window ontology is required.

The generic conceptual operation is:

```text
open native Surface for:
    subject/eventRef
    + MCoordinateRef
    + requested Epi deep product
    + optional current selection
```

The presentation service decides where it appears. Epi determines what it means and what body/provider contract can render it.

## 6. `.0/.5` boundary-expression relation as host metadata, not shell logic

The Epi architecture identifies a repeated 4+2 product law:

- `.0` anchors the domain's ground/source/invariant/identity/reception;
- `.5` anchors its totalisation/render/integration/return seam;
- `.1-.4` are differentiated inner dynamics.

O:I does not infer this structure from coordinates.

Epi SHOULD expose enough native metadata/readings so the parent contribution can state:

```text
boundaryGroundRef      # domain-specific .0 ground
boundaryReturnRef      # domain-specific .5 totalisation/return
parentAvailableActions
parentAvailableInnerReadings
availableDeepSurfaceRef
```

Exact type names are implementation work.

The host's responsibility is only to preserve those refs through selection, Search/Command, Agent co-reference and parent→deep transitions.

## 7. Surface Ledger update

P0 / #104 and later application acceptance must no longer record merely:

```text
Cosmic
Personal
M0′–M5′ deep
```

without product-scale detail.

The minimum Epi ledger now includes:

| Epi product/capability | Required desktop disposition |
|---|---|
| `epi.cosmic.123` | CANVAS |
| `epi.personal.450` | CANVAS plus activity-specific NAVIGATOR / SIDECAR / COMMAND relations |
| Personal Nara journal/write | CANVAS |
| Personal day/dashboard/canvas/flow | CANVAS |
| Personal oracle/reading | CANVAS; Inspector/Agent co-reference |
| canonical Epii dialogue | SIDECAR |
| Bimba/source reveal | NAVIGATOR + KNOWLEDGE + CANVAS |
| `epi.deep.m0` | CANVAS | ALTERNATE-NATIVE |
| `epi.deep.m1` | CANVAS | ALTERNATE-NATIVE |
| `epi.deep.m2` | CANVAS | ALTERNATE-NATIVE |

The ledger must distinguish **current**, **degraded**, **deferred**, and **not human-facing** states rather than using the product design as evidence of implementation.

## 8. C / D / E desktop programme relation

### Prompt C

C is the first native `epi.personal.450` integration.

It should prove the Personal product through current workbench primitives and a single governed subject. It may expose deep M0′/M4′/M5′ refs, but complete deep M′ instruments are not C blockers.

### Prompt D

D owns the Current Situated Matheme and the first native `epi.cosmic.123` integration, binding it to corrected C's same-event Personal relation.

It exposes deep M1′/M2′/M3′ refs but does not claim the whole deep-instrument programme.

### Prompt E

E owns the six deep M′ product surfaces/protocol as a coordinated programme.

From the O:I side, E proves:

- deep-open through ordinary tabs/splits/application services;
- same event/subject/selection co-reference;
- heterogeneous native body support;
- Agent-native open/focus/act over the same refs;
- return from deep to parent without semantic drift;
- full ledger accounting for each implemented/deferred M′ instrument.

E does not rebuild the parent 0/1 product or Current Situated Matheme.

## 9. Agent-native acceptance

For at least one representative path in each implemented product family, prove:

```text
human selection / Action
    and
Agent structured ref / Action
```

address the same native subject.

Representative examples:

- human selects a Cosmic M2 planet/relation; Epii can inspect the same Epi ref and request `epi.deep.m2`;
- human selects a Personal journal range; Epii receives only policy-approved bounded Context and can invoke the same review/oracle/source Actions;
- human opens deep M4; protected handles remain protected and are not copied into workbench global state;
- Agent opens deep M3 through native application service; no DOM scraping is required to recover the current clock/inscription ref.

---

## 10. Explore / shared-world boundary

The eightfold describes the local Epi application field.

It does not make local addressability equivalent to public/shared presentation.

Future Bimba-city, agent-presence or avatar/world representations may participate in Explore only through explicit Projection/Contribution contracts. Protected Nara state stays private unless a separate governed representation is deliberately projected.

This preserves the O:I founding relation between native ownership and shared encounter: the desktop can make another world legible without silently centralising or publishing it.

## 11. Acceptance consequence for the desktop design PR

PR #102 remains valid, but its old shorthand:

```text
0/1 parent
Cosmic M1′+M2′+M3′
M0′–M5′ deep instruments
```

must now be read through this more precise Epi-owned product ontology:

```text
PARENT
  epi.cosmic.123
  epi.personal.450

DEEP
  epi.deep.m0 ... epi.deep.m5
```

The desktop still has one responsibility: **compose native application contributions faithfully**.

The new distinction prevents the host from either flattening Epi's rich depths into generic panes or forcing those depths into the everyday parent experience.
