# Local protocol — one orchestrator, real work, independent checking

Use this procedure with the existing [#65 campaign map](EXISTING-WORK-CAMPAIGN.md), [stories](EXISTING-WORK-STORIES.md) and [participation profile](STORY-PARTICIPATION-PROFILE.md). It coordinates existing tests and native operations. It does not require a new test runtime, finished Factory, a new Agent type or prior full-suite installation before useful preparation begins.

## What you are here to accomplish

Help the person keep using their existing projects, documents, tools and machines with less repeated setup and supervision. Make the selected advanced faculties genuinely usable. Test both the person-facing interaction and what the working Agent actually needs to perceive, discover, decide and execute.

You own the campaign from readiness through testing and bounded repair. The person supplies meaningful choices, permissions and their own assessment—not manual routing between product chats. Your first response after inspecting current state should name a small useful batch and begin it, not return a new multi-agent scheduling problem to the person.

## 1 — Select stories and prepare the actor's actual situation

Begin with ordinary existing-tool use without the O:I desktop, one governance/context task and one knowledge task. They reveal whether installation helps real work rather than merely completing a wizard. Other ready stories may proceed independently. Each approved install composition and materially different placement/interface needs its own applicable variants; do not assume the full desktop proves the smaller setup.

For each selected child story, assemble its existing UX reading plus `extensions.participation`:

- exact story/source basis and original acceptance references;
- actual starting files, project/root scope, subject/Agent identities and environment;
- what each actor may know and access, including explicit exclusions;
- appropriate candidate practices, recognition triggers, determining conditions and actual selected Skills/sets;
- exact required native capability/Action/tool contract and current usable route;
- step effects, untouched invariants, handoff contents, result/readback and continuation;
- expected evidence, local/human gates, finite time/spend/retry bounds and stop conditions.

The person-facing brief remains normal language. For a discovery test do not supply the hidden command, target filename or expected answer that the Agent must find. For a lower-level adapter test, an exact prepared contract is legitimate but is labelled as that narrower test. Do not use it as evidence of independent discovery.

A missing operation is an implementation dependency to fix at its owner. An inaccessible practice is a discovery/loading problem. An absent authorised provider/machine is an environmental readiness condition. Keep them distinct. Do not ask the person to discover known missing prerequisites midway through a supposed ready walk.

## 2 — Use differentiated test roles without inventing extra authority

| Role | Receives | Does | Must not do |
|---|---|---|---|
| Campaign orchestrator | Complete intended story, source map, readiness and bounded testing authority | Prepares cases, allocates disjoint work, monitors actual steps, routes/fixes failures and preserves evidence | Quietly widen a worker's permissions or repair its missing prerequisite and call the original trial unassisted |
| Working Agent under test | Only the normal task/context available to that Agent | Discovers practice, retrieves allowed information, invokes actual operations, handles results and leaves continuation | Receive private oracle answers, unrelated Control or privileged test-only helper instructions |
| Computer-use tester | Human task, visible application and ordinary permitted interactions | Operates real rendered controls/terminal, records interactions and observable state | Call an internal handler instead of the broken control and claim user-interface success; impersonate human consent or subjective experience |
| Independent verifier | Original acceptance, exact artifacts and permission for read/check operations | Checks outcomes/invariants and consequential recovery; attempts a deliberately disconnected-producer case where safe | Accept producer prose as the effect; certify its own implementation as independent proof |
| Repair Agent | Frozen failure, affected native source, scope and bounded authority | Fixes code/configuration/practice in the correct owner and adds a regression | Erase the failed trial, rewrite acceptance to fit its fix, or mutate the actor's live personal state without authority |
| Person | Prepared meaningful choices and actual visible result | Judges purpose, usability and their own experience; authorises consequential source/access decisions | Be treated as a background test worker or as having approved because a simulator clicked a test button |

Roles may be procedures in an existing harness; do not create permanent user Agents for every test. Independent verification requires a fresh suitable participant that did not implement the tested slice. Record lineage and actual information provided. No hidden reasoning collection is needed: source/operation receipts, explicit decisions, artifacts and context boundaries are the evidence.

## 3 — Parallelise only where the resources are independent

Multiple Agents can test different read-only subjects or disjoint disposable environments at once. Allocate separate working copies, NOW/task material, ports, sockets, credential test entries, service names and budgets. Include those allocations in the packet.

One computer-use actor owns the active screen/input stream at a time unless separate real displays/desktops are explicitly isolated. Tests changing the active suite, global harness configuration, machine clock, shared service or common source are serial. Read-only monitoring may overlap them. A parent coordinates shared writes and final integration; passing tests cannot erase required failed/missing legs.

Use the existing Factory orchestration when it actually supplies the required operation. When Factory is the subject still under test, an explicitly bounded external harness orchestrator can perform the campaign. Record that bootstrap; do not fabricate Factory execution or create a second orchestration engine just to run tests.

## 4 — Run the whole story and observe where it actually happens

Use the actual ordinary entry point: native coding tool for silent-use stories; rendered desktop/TUI controls for UI stories; public native APIs for agent-operation stories. The same story may have several such trials. A direct API success can diagnose a UI failure but cannot substitute for it.

Retain the actor-visible task and material revisions, actual selected/context-loaded basis where observable, selected practice and public tool descriptions, invocations, output/effect, user-interface state and durable readback. Attribute messages to their actual recipient and producer. Logs can support inspection; they are not the human result.

Check both desired changes and preserved invariants. Examples: source checks truly ran; the intended Candidate working copy changed; the private file was not disclosed; the other Agent actually received and answered; a prohibited write failed at the actual boundary; remote output is reachable from the caller; original tools still work after removing the integration.

Use the existing CAW runner and native suites when they cover the required behavior. Discover current `scripts/caw_campaign.py --help` and `docs/CONTINUOUS-WORK-PROVING.md`; extend those existing cases rather than make a parallel receipt importer. A subset selection never narrows the parent's scope. Do not import self-written `passed` results in place of recorded operations.

Fixtures can establish repeatable initial conditions, test protocol behavior and exercise deterministic faults. The Agent/provider/app under test must still be the actual required one at its claimed evidence level. A controlled protocol child is not a commercial model, and a model reply is not independent correctness of its work.

## 5 — When a subagent goes wrong, identify the first failed relation

Do not begin with “the Agent did not follow instructions.” Use the actual step packet and captured evidence:

| First discrepancy | Check | Repair at |
|---|---|---|
| Wrong task, project or authority context | Actual brief, root/child resolution, selected identity and permissions | Orientation/resolver or packet preparation; preserve distinction between test error and product error |
| Needed information absent or inappropriate material included | Eligible/retrieved/disclosed/loaded source revisions and exclusions | Native source/context path; restore privacy before resuming |
| Appropriate practice not found or wrong lookalike selected | Actual description, catalogue, selection, projection, link and loaded body | Canonical Skill description/source/discovery or existing accepted release procedure |
| Practice understood but operation unavailable | Descriptor, installed version, provider support, credential/grant, required protection | Native capability/adapter/install/material owner, not optimistic Skill prose |
| Claimed send but recipient did not act | Request routing, receipt, actual resident invocation and response | Native dispatch/transport/continuation owner |
| Operation reached code but effect is wrong | Exact input, source basis, effect/readback and invariants | Native implementation or formal operator; a deterministic invariant needs executable correction |
| API effect correct but interface misleading/unusable | Rendered interaction, focus, stale state, error/repair control | Existing desktop/TUI owner lane |
| Observation invalidates the expected answer | Original intent and authoritative domain source, not implementer's summary | Record a sourced design question; do not silently rewrite the oracle |
| Outcome uncertain after interruption | Last committed cursor, actual external effects, pending obligations | Native reconcile/recovery before any retry; silence is not absence |

Freeze the failing trial before assistance. Record actual intervention, not just a green second run. Preserve what remains usable; stop or isolate only affected work. Escalate only unresolved authority, meaning or irreversible consequence. An unavailable test tool is an exact environment limit, not proof the feature is absent.

Implement the bounded repair at the real owner and keep live desktop/Actuation integration ownership intact. Add a focused regression, run relevant owner tests, then rerun the entire affected story from a fresh independent starting state. A helper prompt that tells the worker the missing answer may be useful diagnosis; it invalidates an unassisted-discovery claim for that trial.

Repeated model-based trials should declare input/seed/model/context changes and any sampling rule before interpreting success. Keep failures and variance. Do not cherry-pick the first good answer or invent a universal performance score.

## 6 — Evidence, retention and the person's report

Keep existing D/C/P/M/H meanings. Record controlled technical checks, real provider use, actual installed/material behavior and human EX separately. Computer-use evidence says which real controls it operated and what happened; it cannot state that the person found the experience satisfying.

The run record needs the exact UX/step/variant, source/capability/practice and tested cut, environment/actor, observed effect, preserved invariants, failure/assistance, independent result and remaining decision. Use native records and existing evidence envelopes. Screenshots/transcripts that contain private source remain local; publish only reviewed bounded/redacted references and diagnostics.

Consolidate the human account plainly: “The assistant used the project's checks and fixed the bug. Your working notes are unchanged. Its attempt to open the restricted folder was denied. One new-session loading issue is still open.” Deeper technical records remain available behind that account.

Keep operational ledger prose lean using the existing `central-ledger` practice where actually available. Budgets do not limit the substantive plan, source stories or human writing. Archive via current native retention rules, preserving pending work, failed evidence and exact later re-entry. No background recurring task is created without a separate authorised trigger and scope.
