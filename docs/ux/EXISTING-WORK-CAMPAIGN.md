## 0 — The experience and its sources

A person already has work, files, tools, habits and collaborators. They install the parts that help, continue working in their chosen tools, and open O:I's own interfaces when useful. Relevant instructions and knowledge reach the right Agents; ordinary work does not require repeated setup, pasting context or watching a dashboard. When something fails, the person can understand what is affected and continue safely. Deeper knowledge, collaboration, development and formal faculties remain available without becoming a minimum admission requirement.

The Agent side of that same activity is equally concrete. An Agent finds the actual task and scope, discovers the appropriate practice, retrieves the permitted material, chooses among the available operations, acts, understands the response, repairs or escalates an actual obstacle, and leaves work another participant can resume. Instructions, tool descriptions, skill descriptions, context and feedback are its interface. Availability on paper is not operative competence.

This is the authorised breadth correction to the earlier CAW-only account. CAW and the Cradle everyday loop remain substantial parts of the campaign, not the definition of all O:I use. This document coordinates existing acceptance; it does not replace product positions, the desktop design, native capabilities or their existing tests.

## 1 — What is mapped, and what is not being claimed

The catalogue contains parent activities and atomic child stories. Each child has a human task, material starting condition, Agent context/practice obligation, expected effect/readback and a meaningful failure/recovery branch. Family bindings name source authorities, native capabilities and existing proving homes. The participation profile makes those links machine-readable without making the story an executable permission grant.

Coverage is bidirectional:

1. Every story's required capabilities/practices are linked to actual owner records or an explicit unresolved binding.
2. Every in-scope capability, existing acceptance obligation and formal inventory entry has a story, a transitive support link, or an explicit applicability/future disposition. Internal facilities may support another capability; do not invent a human button for each function.

The published catalogue covers the whole requested activity field. It is not a claim that every low-level owner operation has already been bound or exercised. CP0 imports the exact selected owner inventories and exposes any remaining unlinked entries. No family-level success discharges its children. No overall percentage disguises missing high-consequence cases.

### Source and representation

Readable stories are authoritative for this campaign at `EXISTING-WORK-STORIES.md`; the adjacent binding register supplies exact technical links without repeating their prose. CSV/JSON views are derived through the existing matrix/UX contracts. Native capability identities and authored meanings remain at their owners. Do not replace source files with generated copies to make ingestion convenient.

Each scheduled test freezes the story revision and its actual binding packet. Later clarification or repair records a new revision without silently changing the expected result of a failed run. An unresolved design choice is brought to the owner before testing it as a requirement.

### Required adoption axes

Do not confuse these dimensions:

- **Installation history/path:** the six currently named mechanisms (`fresh-ground`, `existing-ground-reconcile`, `developer-source`, `existing-world-adoption`, `reference-world-host`, `harness-strap`). `unknown` is historical missing information, not a seventh product offering.
- **Chosen composition:** the source-defined CF1–CF7 arrangements, including the owner's desktop `00/00`, minimal `0/1`, common `0/1/2` and developmental `0/1/2/3` cases. #29 records CF5 recursive contextualisation, CF6 nested/outward relation and CF7 closing/reopening. Resolve their exact current supported recipes from the owner; do not infer a package list merely from the numerals.
- **Interaction:** ordinary existing tool with no O:I UI; CLI; TUI; desktop; headless/background; another human's selectively shared interface.
- **Placement:** ordinary local machine; constrained process/container/VM; remote host; persistent service; GPU/model-serving arrangement where supported.

Every approved CF composition gets an explicit declaration of required/optional/absent products, first useful activity, retained native configuration, removal/upgrade behavior and unavailable-function explanation. A proof of a modality label does not prove its composition. Missing CF-to-install binding is a visible owner task, not a guessed fixture and not a reason to stop other valid variants.

Test combinations that alter semantics, permissions, persistence, reachability or human interaction. Record why an untested combination is inapplicable or covered by a proven equivalence; do not claim an exhaustive cross-product from a few samples. Optional QL absence is tested independently; optionality does not reduce full QL coverage when selected.

## 3 — The operating Wayfinder

These are execution units of #65, not six new products or a replacement Agent runtime.

### CP0 — Select the real field and bind the first runnable stories

Read this map and current owner acceptance. Inspect the real local machine without mutation; preserve private source. Identify the chosen composition and ordinary tools, available tester interfaces and existing campaigns. Pin original document fixtures and relevant source/Skill/capability revisions.

Import native capability records and original acceptance IDs. Bind a useful first batch of stories; record unresolved links for the remainder in the existing campaign ledger. Start safe observation and disposable tests immediately. Do not spend the session building a total inventory before demonstrating one useful operation.

Output: one selected-cut/World record; story-to-capability/practice bindings; declared simulation/material facts; readiness per story; exact gaps, not a second master status database.

### CP1 — Make the story packets usable by test Agents

Use the profile in `STORY-PARTICIPATION-PROFILE.md` and the existing UX fields. Resolve native capability, Skill, Action and source refs through actual providers, or explicitly read the exact source as a bounded bootstrap. Write any missing reader/validator support as an extension of the existing campaign and native Knowledge/source path, not an unrelated runtime.

Test the packet itself: a fresh Agent receives only the actor-visible brief, finds needed sources and practices, rejects a near-miss practice, observes a missing permission, and leaves enough evidence for a different verifier. Private expected answers and fault-injection details stay with the verifier. Schema validity never proves a good task outcome.

Output: runner-readable packets, explicit inherited/local context, callable checks or named unsupported joins, and automated structural/negative validation. A not-yet-implemented native ingestion route is labelled as such; Markdown instructions are not claimed as installed API support.

### CP2 — Exercise ordinary work and individual faculties

Run the installation/quiet-use/governance/Agent/knowledge/writing/practice stories on disposable realistic arrangements and then the chosen personal setup under its authorised plan. Preserve normal native entry points and independent files. Exercise each participating product's own operations as needed, not just a Factory wrapper.

Parallelism is by disjoint writable resources and evidence: separate repositories/checkouts, test roots, conversations, credential test entries, material allocations, ports and budgets. One UI operator owns a desktop at a time. Read-only verification can overlap; tests changing shared global configuration, time or active suite state cannot.

Output: actual observations, failed/blocked branches and compact human-readable explanations. The next stage may start for ready stories without declaring unready families complete.

### CP3 — Exercise collaboration, long work and deeper intelligence

Complete two-Agent cross-harness work, planned independent verification, recurring work, headless operation and later continuation. Use real tasks and different inputs rather than fixed replies. Extend to two independently grounded users, remote machines, third-party extensions and the selected QL/Epi field using their existing owners.

The full formal inventories remain explicit required children for that scope. Do not gate ordinary system use on their completion, and do not silently mark them covered by the generic no-QL case. The original six Guardian Agent names and current stable identities are preserved; tests may create disposable Agents through the actual creation operation without replacing the user's Agents.

Output: complete native operations in their actual environment, plus source-backed reasoning assessments and genuinely human reports where supplied.

### CP4 — Fail, diagnose, repair and rerun without disguising the failure

At a failed step retain the starting state, actor-visible inputs, public operation, observed output/effect and last successful handoff. The orchestrator identifies the earliest broken relation: wrong orientation, unavailable/inaccessible context, undiscoverable practice, incompatible or ungranted capability, transport/execution, material condition, stale source, UI projection or invalid test assumption.

Do not decide that an Agent disobeyed just because the result is wrong. First establish what it actually received, discovered and was allowed/capable to do. Conversely, a valid API does not prove the Agent used it. Fix deterministic invariants at their owner; improve descriptions/practices where they caused the failure; ask the person only about genuinely unresolved meaning or authority.

Repair in a separate bounded worktree/branch or authorised configuration operation. Preserve failed evidence, revise the tested cut, retest the failed seam and rerun the whole affected story from an independent starting state. Assisted completion is recorded as assisted. A fresh independent verifier retests without the hidden assistance before claiming ordinary usability.

Output: concise diagnosis, native repair/evidence, regression, fresh story result and unchanged wider obligations. The human is not required to relay the defect between A–E chats.

### CP5 — Independent acceptance and normal continued use

A fresh verifier that did not implement the operation tests the original story and a consequential recovery branch. A computer-use Agent may operate a real interface; it reports its own observed evidence, never a human's experience. The person judges intelligibility, attention burden, expressive freedom and decisions reserved to them.

Close a story only at its declared evidence level. Scope-level completion requires every included child/variant and required original proving obligation to be accounted for. Preserve legitimate unresolved, blocked, excluded-by-scope and human-unassessed cases instead of compressing them into green.

The phrase **usable end-to-end feature.** is reserved for that full named acceptance object. It is not a parser switch or a blanket suite certificate. The campaign itself may continue across releases.

## 4 — What runs where, and how setup remains safe

**The sane model split is by what kind of reality can prove the work.**

Repository code, source-contract checks, temporary real Git/filesystem work, controlled clocks, adapter conformance and automated UI tests run wherever the tools support them, including GPT web and CI. Lack of the user's credentials or desktop does not block writing those implementations. Controlled replies do not prove real model use.

Local harnesses operate the installed product, existing private configuration, actual processes/services, native Agent tools, chosen remote host and real computer-use interface. Most of that can be automated. Human assessment is the part requiring the person, not every local test.

Converge only the selected accepted product lines, account for active exceptions, and preserve dirty/staged/untracked work. Inspect squash/rebase ancestry and unique changes before retirement. Check that required operations/tests survived the convergence. Do not rewrite shared history or merge unrelated unfinished work to make the tree look clean.

Record source → build → installed registration → actually invoked executable → resident companion process → effective practice/loading. Reuse unchanged verified artifacts; coherent activation does not require needlessly rebuilding every product on each repair. Hold one campaign cut fixed, then explicitly revise it for repairs and rerun affected proof.

A local enrolment or update is not automatically authority to adopt private governance, erase folders, transmit private source, spend money, expose a service publicly or grant unrestricted tools. Use bounded existing grants and one concise clarification where genuinely required. Test fault injection in disposable/approved specimens; never disable the person's real protection to obtain a pass.

The existing #190 desktop wave plan remains the UI implementation owner. This campaign adds acceptance coverage, not a new shell or duplicate chat/source store. Each control must have its user story, actual native operation, visible/structured result and failure path. Preserve original source files and stable selections through panes, tabs, splits, full views and detachment.

Graph tests exercise real relations and source changes, not just node counts. Computer-use tests use rendered controls for user-interface claims; the developer walk channel may inspect state but must not silently bypass the tested control.

Run the no-desktop composition too. A successful full desktop experience does not certify that silent installation, ordinary tool integration or independent native product use works. Conversely the optional desktop's absence cannot fail those scenarios.

The local handoff is one orchestrator with the protocol below, existing Skills and native owners. It chooses ready batches, manages subagents, retains original evidence and makes repairs. It reports useful results and only consequential human choices. No recurring automation is installed merely by publishing this plan.
