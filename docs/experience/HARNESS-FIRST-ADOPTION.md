The original AD/WK/GV/AG/PX/DV/UI stories and their full native obligations remain. [harness-first-adoption.json](harness-first-adoption.json) binds the clauses below to those existing stories. ## 1. The experience and its two entrances

> I am already talking to an agent in my usual coding harness. I paste the O:I adoption request. The agent explains what it found and what the proposed additions do, connects the useful parts without disturbing my work, tells me whether this session needs reloading, and verifies the result by helping me do real work. I can keep using this harness or subsequently open the same work through O:I.

There are two first-class entrances into the same native field:

```text
existing harness conversation                  O:I / AIKit launch
  recognise and retain its native body          resolve and start the chosen body
  adopt/project only what is supported          establish native session/place bindings
                         \                     /
                   permitted Project / source / praxis
                         actual body and model
                    native authority and Activity
                       useful result and Return
```

Neither route is a prerequisite for the other. A supported external harness can be retained and provisioned without being relaunched inside an O:I terminal. Observation of a process alone does not establish an AgentSession, stream or Factory execution. Where a running external conversation cannot be adopted, retain its work, disclose the limit and prepare an explicit continuation; do not fabricate historical events or session continuity.

A person's immediate question is what this enables and what changes, not which abstract installation class to select. Treat **engagement facets** as human-facing readings of useful participation: durable ground, situated agency, resolved practice, organised development, remote access, desktop presentation and hosted learning. Exact requested/effective/installed composition, permissions, native frame identity and historical receipts remain explicit underneath. This is not an instruction to rename wire enums or modify QL coordinates.

For this harness-first journey the proposed operational core is **Central + Actuation + AIKit, 0/1/2**, with the `oi` doorway. The person can accept that plan, retain compatible existing owners, or select less. Factory, Desktop and QL are not hidden prerequisites for ordinary core work. **5/0 remains the hosted Library/Expression/corpus encounter**: a browser visit, not another visitor installation. The reader and the host have different deployment responsibilities.

## 2. From pasted request to working adoption

### A. Receive the request in the existing harness

Start with the current user purpose, directory/Project where known, harness edition/version and available execution faculties. A pasted request is the entry, not proof that the target already has terminal access or permission to install software. Where the conversation cannot execute locally, explain the exact local step or supported connector required; never imply that a text-only response changed the machine.

The adoption guide itself must be reachable without an already-installed O:I Skill. The commissioned bootstrap can explicitly read a source-qualified public guide. Verify the source and installation provenance using the supported distribution route. Record that explicit bootstrap separately from later native Skill discovery. Do not use successful pre-provisioned testing to claim that cold adoption works.

### B. Explain the plan before mutation

Read-only recognition identifies the existing harness and native configuration, installed owners, Project and source roots, Skills/agents, adapters, credentials by reference and material constraints. Existing-world recognition is not adoption by copying everything into another hierarchy.

Present a concise human account of the exact proposed work:

| Addition | Practical purpose | What must be explained |
|---|---|---|
| `oi` | One doorway for discovering and composing the native products | Actual bootstrap/distribution source, install location and managed ownership |
| Central | Durable human and Project ground, source and continuation | Existing or new root, in-place binding versus optional relocation, preserved authored material |
| Actuation | Attributable agency, execution bounds and returned activity | The actual native body/authority relation, not a new permission granted by installation |
| AIKit | Resolve and deliver the relevant context, Skills, tools and harness configuration | Source scope, selected repertoire, projection destinations, hooks and activation timing |
| Default Skills and existing Guardian definitions | Explain and operate the resulting world and its selected products | Name, purpose, source, scope, proposed default and actual activation; installation is not permission to start agents |

Keep detailed refs/diffs/evidence available without making the person read a diagnostic dump. Disclose required prerequisites honestly: a release bootstrap, an existing compatible owner and a current-source build have different requirements. A missing public bootstrap artifact or required companion is a product gap, not a reason to silently substitute an old release or hand-copy binaries.

Choices remain useful: cancel, decline a product, retain native settings, defer credentials or postpone a restart. Ordinary permissions already covered by the accepted bounded plan do not require a fresh approval at every internal step.

### C. Establish or reconcile native ground

Central owns root and ProjectCentral discovery, inspection, planning, application and readback. Keep existing Projects and instructions in place where the actual native binding permits it. Relocation or migration is a deliberate, reversible choice, not an incidental side effect of entering O:I. Preview its scope, preserve Git worktree relations, uncommitted files, source exclusions and native harness configuration, and test interrupted/repeated migration on disposable material first.

Human-authored instructions remain human source. Agent-maintained knowledge, imported native Skills, generated projections and observations retain their different standing. Reconcile existing agents by native identity and source rather than minting duplicates from matching names. Central is the root meta-Project; a fake child Project is not needed to explain root work.

### D. Deliver the selected practice and defaults

Use the actual current O:I bootstrap manifest and AIKit's native source/trust/set/scope mechanism. At this source inspection `skills/suite-operator/skillset.toml` has **three O:I-owned Skills**: `oi:skill:operate-suite`, `oi:skill:suite-operator` and `oi:skill:central-session-strap`. O:I holds and projects the strap from `skills/central-session-strap/SKILL.md`; harness copies are receipt-gated derived projections. Reinspect the authoritative manifest at execution; this count is not a new invariant over all future product development.

A SkillSet is not an AgentSet. Explain each selected Skill or Method's purpose and relevant trigger; explain existing Guardian agents' role and selected defaults separately. Resolve their current native source/default refs and product-operating repertoires. No copied foreign manuals, replacement Guardian identities, automatic invocation of all Guardians, or private Control material in shared evidence. A Method remains a Skill whose description begins `METHOD:`.

Stage target-native changes with provenance and owned update/retraction boundaries. Preserve user-installed extensions and user edits. Standing guidance should orient the agent into the addressable world, not load every product manual into every turn.

### E. Install hooks and project through the real adapter

AIKit #114 supplies the admission lifecycle: discover → plan → project → activate/reload → verify → explain → update/retract. Test actual harness edition and capabilities, not brand-name assumptions.

For each supported hook or projection, account for its event/trigger, source revision, scope, destination, order/composition with existing hooks, permitted effect, cost, timeout, failure behaviour and removal. Preserve the target's native mechanics. Repeat adoption idempotently; never duplicate callbacks, recurse into a new strap on each hook or override foreign configuration. Missing hooks remain explicit capabilities rather than invented configuration keys.

Keep separate: source availability, selected resolution, written projection, registered hook, activation observation and effective use. A file's existence, a symlink, a successful hook command or a test receipt is not enough to establish the agent actually received the intended context. Source/hook changes must not start unrequested model work or forward an entire private conversation into telemetry.

### F. Explain activation and preserve continuation

A target can support live reload, next-turn lookup, next-session loading, restart-only loading, or a narrower observed behaviour. The adapter's actual contract determines which applies. Tell the person what is already active, what is pending, the affected session, what to save, and how to resume. Do not kill or restart their current harness just to make a check green.

For restart-only targets, retain the original task/Project/continuation refs, give the exact target-native restart/resume step, then verify the new session's actual loaded source and hooks. Where provider continuity cannot be retained, name the successor session and what context was deliberately reconstituted. Updating a pointer does not retroactively change past acts or prove hot loading.

### G. Prove the first useful task

Return to the person's original work. In a fresh or legitimately reloaded agent context, perform a small real task requiring the selected Project guidance, knowledge and a public native operation. Observe the resulting effect, correct scope and refusal boundary. Keep expected answers and private canaries with the independent verifier, not in the actor's prompt.

Explain the outcome in ordinary language: which harness/model was actually used, what practice was received, what changed, where the result lives and what remains unavailable. The current user-selected native model may stay native; a routed model uses the actual supported resolution path. Distinguish requested, resolved and observed model/provider facts, credential availability and any explicitly permitted fallback. Do not silently change provider, cost or execution location to pass the test.

## 3. From ordinary work into SessionSpaces and Factory

Test external-harness entry and O:I-started SessionSpaces independently, then their supported joins. The adopted Project, source, effective context, Agent/Agency, native provider session, canonical AgentSession, SessionSpace, working Surface and material process are related identities, not interchangeable labels.

For ordinary external work, correlate only what the adapter actually observes or binds. For an O:I launch, retain the exact chosen harness/model/environment, initial source/practice basis, bounded authority, launch result and continuation. Switching a UI arrangement or focusing an external window does not start another agent.

Chat passthrough must carry a real request to its actual selected recipient/body and return the actual response, tool/permission effects, interruption and finish state through the supported stream. Retain native event ordering/cursors and disclose event coverage or gaps; do not manufacture pre-adoption ActuationStream history. Test two concurrent sessions with different scope/model choices, out-of-order or duplicate delivery, cancellation and reconnect.

When the person deliberately commissions Factory work, add the genuine Commission/Journey/Run/attempt/execution relation, independent verification and Return. An existing chat, process or streamed answer is not retrospectively a Factory run. Closing a pane is not cancellation; an update of installed binaries is not a restart of residents. Day/NOW and effective historical context continue through the current owner contracts. Feedback and subsequent repairs use the same retained activity rather than a second telemetry store.

The app's human face consumes these native operations. Preserve #375's active new-UI destination and current Factory centre Chat ↔ full Run with Run / Agents / Context. This document commissions no shell/CSS rewrite or merger of an unfinished app branch.

## 4. Unsupported targets, refusal and withdrawal

An unrecognised edition returns its observed faculties, the missing adapter/contract, public SDK/authoring Skill and conformance route, with the work required to support it. Offer that route clearly. Actual adapter development and installation need their own bounded authority; availability of an authoring Skill grants neither.

Where authorised: inspect the real target → implement via the owner SDK → conformance → register/package → repeat admission → perform the same useful task. A fake target is useful SDK conformance, not evidence for an unsupported real brand. Retain any independent ordinary native use while an optional integration is unavailable.

Test cancel/retry, conflicting user files, partial install/projection, hook failure, denied/expired access, deferred restart and remove/update/retract. Remove only integration-owned material, leaving native agents, Skills, settings, personal source and useful results intact. Degraded integration should name its consequence and next supported act, rather than show an empty screen or falsely announce success.

## 5. The current Mac cut is a separate activity

The owner now commissions a bounded current-native cut across Omarchy/remote and Mac. It is **not a cold install** and must not become a re-bootstrap of the personal ground.

- **Update candidates:** `oi` plus Central, Actuation, AIKit, Factory and Workcell. Account for all six product positions; **QL-MEF is held unchanged** at its actual installed/source basis for this cut.
- **Protected:** QL repository/branches/M/M′ bodies, installed QL artifacts/registrations and required resources; active Cradle/app/UI branches, app generation, drafts and resident work. Do not solve a host/API mismatch by merging the unfinished app or changing QL. Record that exact dependency.
- **Reconcile:** inspect actual GitHub and both-machine source/installed/running state for the selected owners; preserve and account for unique unpublished non-UI work; continue compatible feature lines and verify their accepted increments. Mainline publication and explicitly selected unmerged candidates have different standing.
- **Install authority:** [INSTALL-UPDATE-FLOW.md](../INSTALL-UPDATE-FLOW.md), its current native implementation and real CLI help. `oi update` uses the committed HEAD of the discovered Work checkout, exports with `git archive`, builds via native declarations, stages content-addressed generations and records `oi.managed-update/v1`. Dirty files are preserved, not installed. The command does not independently establish that HEAD is the intended accepted cut: the integration lead must do that first.
- **Scope:** use the real updater's explicit product selection; inspect the planned exact allow-list before applying. An unscoped update, whole-suite source-sync, cleanup or rollback can touch protected QL. No such operation is authorised by this cut. A held QL entry must survive receipt changes as well as binary changes; verify before/after hashes, activation targets and registration identity. If the tool cannot preserve that boundary, repair its selection/retention seam under the existing owner before applying, not by manually editing receipts.
- **Material:** the Mac builds/receives artifacts for its actual OS/architecture through the supported managed path. Linux binaries are not Mac artifacts. Preserve bounded native build caches and avoid duplicated dependency/build trees. The immutable historical released suite and clean-main-only `oi dev install` are different routes, not substitutes for the managed current-source update.
- **Complete installation:** include every declared companion executable, runtime/source/Skill resource and dispatcher target, not merely the primary binary. Verify PATH and GUI/headless launch environments against actual managed targets. Do not patch over missing installation by hand-copying a binary or rewriting a manifest to claim an unbuilt revision.
- **Residents:** atomic replacement preserves already-running old processes. Record which process/provider generation is still old and coordinate any necessary targeted restart/rebind without losing tasks. Never claim running currency from the newly resolved CLI version alone.

Return one exact selected candidate record through the existing suite/#65 evidence path: accepted source or explicitly qualified candidate revision; built/adopted artifact; installation/activation; running provider; known app consumer basis; held QL basis; tests and remaining gap. The full excluded QL and UI obligations remain in their existing tracks; they are not renamed absent, failed, complete or optional merely to produce a whole-suite green result.

## 6. Parallel worktrees, sandboxes and the follow-on campaign

**One reusable code worktree per coherent feature/development line, not per agent, session, retry or test.** Multiple agents on that line share it with explicit file claims and serial Git/index/checkout/commit operations. Prefer existing suitable worktrees. A new worktree requires a genuinely independent line or incompatible candidate basis, not just another worker. Do not delete an active worktree at the end of one agent's session.

Disposable test worlds are separate from code-worktree allocation. Use the existing Omarchy sandbox/provider facility under [LOCAL-CAMPAIGN §2.1](LOCAL-CAMPAIGN.md#21-omarchy-sandbox-proving--available-development-material). Share compatible caches safely, bound resources, retain evidence outside guest deletion and clean only owned material. The Mac remains the accepted installed/ordinary-use locus, with the owner's frontend work protected. Mac-native packaging/provider/GUI evidence and two-physical-host evidence retain their real scope.

After the candidate is pinned, three disjoint proving assignments may run together under #65:

1. **Harness-first adoption:** cold/bootstrap and existing-world paths, source/Skill/Guardian explanation, projection/hooks, activation/restart, ordinary task, unknown-target SDK path and clean retraction.
2. **Session/routing/Factory use:** externally entered versus O:I-started sessions, actual model/recipient routing and streaming, independent Direct/Factory ancestry, app consumer behaviour, original-context/result/NOW Return and recovery.
3. **Install/lifecycle resilience:** selective update including companions, exact activation/receipt/provider readback, compatible partial compositions, interrupted install/update, supported rollback/recovery and owned teardown in isolated environments.

Source/kernel tests and isolated preparation can run while the Mac cut is assembled; installed cross-product verdicts bind the exact returned cut. Shared host services, registries, data and desktop focus are serialized. Consume the actual Day/NOW foundation return for dependent cases without repeating completed setup; missing support blocks its particular case rather than all independent work. No intermediate human-ratification gate is introduced.

Use the technology first. Preserve observed failures, improve the responsible native product/adapter/Skill/test, then independently replay the original and held-out cases on the new exact cut. Test the verifier with a disconnected operation, stale model/source response or unloaded projection. Do not weaken source-defined expectations to pass. Runtime repairs land with native owners; UI-facing read models, explanations and recovery actions go to the existing new-UI integrator.
