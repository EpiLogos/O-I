## The one containing frame

**CF5, `4.0/1–4.4/5`, is the material nesting frame in which the other six forms are situated.** Some computer/material environment is always the condition. Installing the Workcell management product to a greater or lesser degree is a separate choice. All-products deployment, with or without desktop, is supported inside that frame; it is not what makes CF5 exist.

Every episode records actual material placement even when no Workcell daemon/VM/management package is installed. It does not fabricate a registered Workcell identity when the native relationship is unavailable; it records the actual external/local condition honestly.

## Cross-form interaction stories

These remain branches of AD08/AD09, MC and DV, not a linear upgrade ladder:

1. **Add or remove a surface.** Start with useful headless work, attach the desktop, inspect/edit permitted material, detach/remove it and continue in the native tool. No source duplication or forced session restart merely from presentation.
2. **Add a capability and later withdraw it.** Move between actual chosen combinations through their owner operations; preserve identity, history and configuration. Show effects on pending work before removal.
3. **Separate three operations.** A software update changes selected installed software. Source synchronisation changes only explicitly selected source with direction/conflict/authority. Material reconnection re-establishes a supported connection/lease. An “update” must not silently do all three.
4. **Change machine, not identity.** Open the same remote work from a second permitted client; document the source and continuation actually available rather than assuming identical local installs.
5. **Remove and explain residue.** Preserve pre-existing native programs, personal source and useful artifacts. Revoke only owned access and release only owned resources. A purge of disposable tests needs its own specific authority.
6. **Historical evidence.** Read an old receipt without relabelling its composition. New readings use the corrected current-world contract; source/time/code changes remain explicit.

## Preparation and closure

Use `campaign.json`'s `installation_composition` as the planning projection of #268. Record requested/effective/installed composition, native alternatives, surface, environment, authority and actual lifecycle evidence. Never infer them from a CF string or product count.

The local operator can prepare and test disjoint disposable composition specimens in parallel, but cannot concurrently mutate one person's installation or drive the same desktop focus. The daily-use machine remains protected; physical second-machine access is not authorisation for destructive testing.

Native #268 implementation and its tests own composition/lifecycle behaviour. The #65 campaign verifies the person's first use, ordinary repeat use, failure/recovery, change and teardown for each promised form. Static planning validation proves only that the source requirements were retained. Missing production operations stay with the connective implementation lane; the human should not discover preventable prerequisites halfway through a test.
