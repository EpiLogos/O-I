# Local operator: prove useful work from both sides

Start at [#65 and the campaign map](README.md). Use [stories](STORIES.md), [paired record profile](STORY-PROFILE.md) and [practice conditions](PRACTICE-CONDITIONS.md). Load the source-owned [campaign Method](../../skills/experience-campaign/SKILL.md) explicitly for this commissioned bootstrap when it is not yet discoverable through the actual installed AIKit source. That explicit load is not a claim that normal discovery works.

## 1. Your job and why it exists

Make it possible for the person to use their own tools and files with reliable help from agents. Verify each selected activity through the normal human and agent entry, locate failures precisely, repair authorised defects at the native owner and repeat the real activity. The desired output is usable work and an understandable account, not a collection of green names.

You are the **one campaign orchestrator**. Product ownership determines where a repair belongs; it does not require the person to send messages between product chats. Reuse existing native tests, CAW P01–P28, TUI/desktop walks, provider conformance and QL checks. Do not build a second scheduler, test-result database, Skill registry or runtime.

Keep one concise current entry under #65 linking the exact round, active test assignments, current source/installed cut, real blockers, original failures and next steps. Native code/contract fixes and their evidence remain with the owner issues. Day/NOW entries point to these sources rather than retell the entire investigation.

## 2. Before asking the person to test

1. **Inspect safely.** Read actual local/remote state, relevant owner issues and approved source; do not re-run a whole-suite census before every small operation. Preserve dirty/untracked/staged work, local customisations, active worktrees, processes and pending results. A closed issue is neither a reason to repeat its completed implementation nor sufficient proof of this installed experience.
2. **Select a coherent round.** Account for all required product versions and companions. The first tasks are ordinary quiet use, instructions and a real agent, not necessarily the largest Factory or QL demonstration. Choose the relevant setup context, selected/declined products, familiar user entry, root/child scope and machine. Ordinary absent optional products must stay absent in their tests.
3. **Resolve readiness.** For each chosen row, bind actual native capabilities, current schema/input/result, context sources, applicable Skills/sets, exact revisions, loading route, authority and material support. A plan names requirements; a real invocation/readback establishes them. An unavailable UI, tool or computer-use channel is a precisely named test-environment gap, not simulated access.
4. **Use the final cut.** Reconcile required code/branches under existing policy; run final-source tests; build and verify installed paths and resident service versions. Do not force-merge actively owned QL/desktop work or rewrite shared history to achieve cosmetic cleanliness. Use isolated build outputs/acceptance worktrees. Hold this cut fixed during an episode; repair changing it creates a new episode and affected retesting.
5. **Prepare disposable material first.** Use realistic copied or purpose-made examples with known important distinctions, not only tiny canned success fixtures. Record filenames/versions and invariants outside the actor brief. Rehearse migration and destructive failure conditions in disposable environments before specifically authorised personal application. Select private-canary tests without exposing canaries to the working actor.
6. **Check safety and capacity.** Set explicit time/turn/cost/concurrency/resource/retry limits for this round; record which effects, external transmissions, credentials, machine restarts and repository writes are permitted. No fixed global allowance is inferred from this document. Have an emergency stop and known cleanup/retention boundaries before starting a multi-agent or computer-use run.

A missing production operation remains implementation work. Do not invite the human into a control known to have no working route. Complete it, or select a useful independent activity while preserving that obligation as blocked. Human judgement is reserved for actual choices and experience, not avoidable setup debugging.

## 3. Roles in one episode

The roles can be implemented with the available local orchestrator/subagent/harness facilities. They are assignments, not new permanent system Agent types.

| Role | Receives | May do | Must not do |
|---|---|---|---|
| Orchestrator | Original story/source, dependencies, safety bounds, all permitted observations | Prepare, schedule disjoint episodes, stop affected work, locate seams, commission bounded repair, retain one handoff | Covertly fix setup during a run and label the original attempt unassisted; infer missing authority |
| Working agent(s) | Realistic request, permitted actual project/material, ordinarily discoverable instructions/tools | Discover applicable practice/context and perform the task through real routes | Receive hidden expected answers, verifier canaries or special private helper operations absent from ordinary use |
| Computer-use driver | User-facing task and real visible application/session | Use actual pointer/keyboard/accessibility affordances, inspect displayed state and preserve interaction trace | Call hidden state mutation APIs and label the result a UI walk; impersonate the human's quality judgement |
| Read-only witness | Relevant before/after state and authorised native evidence | Observe actual file/process/source/task effects and correlate steps | Mutate the subject being measured or reveal private expected-answer material to the actor |
| Repair worker | Frozen failure, exact source/capability/Skill basis, bounded owner issue | Diagnose/implement/test a specific native repair under existing code authority | Change the story's intended success to fit the code, clobber active writers, grant itself wider access |
| Independent verifier | Original requirements, scope/cut, resulting artifacts and appropriate observation access | Reproduce the full required route and meaningful negative case | Accept the implementer's summary as its own proof or self-certify a feature it implemented |
| Person | Clear choices, real outputs, comparison and relevant evidence depth | Decide actual authorship/access/design questions and provide personal experience assessment | Be expected to coordinate product dependencies or inspect every routine event |

Where a computer-use tool is unavailable, use native/API tests for their actual scope and leave UI proof pending. Never pretend API calls are clicks. Where a real second person is unavailable, independent isolated technical accounts prove their access behavior but not two-human collaboration quality.

## 4. Run the normal route and observe the handoffs

Start the actor with the story as an ordinary user would. During the trial, retain bounded observations at these seams where relevant:

```text
request/selection
  -> discovered task and source
  -> applicable practice and current context
  -> native capability/input and permission
  -> chosen model/harness/machine/working copy
  -> actual effect or refusal
  -> another participant's real receipt/work/reply
  -> actual result and independent check
  -> visible useful outcome
  -> durable continuation in later work
```

Do not require invisible private reasoning. Evidence is actual prompts/context disclosed where permissible, tool and operation inputs/results, sources, logs/events within scope, screenshots, filesystem/process/network readback and returned artifacts. The same subject/revision must be followed across the human and agent faces. If only one seam has telemetry, retain the unobserved part as unknown instead of inferring a full chain.

For quiet-use tests the driver may never open the O:I desktop. The benefit is demonstrated when the normal harness discovers and uses the relevant instruction/knowledge/resource in useful work. Instrument the prohibited side effects too: unwanted source rewrites, unrequested model invocations, secret leakage or spurious Factory tasks are failures, even if the main answer looks good.

For graph/intelligence tests, give actual documents with relations, changes and disagreement. Let the acting agent find them using normal search. Keep oracle filenames/expected dependencies outside its context. A verifier checks retrieved sources, the substantive result and the dependencies used; merely emitting a graph or a polished paragraph is insufficient.

## 5. When a subagent or seam goes wrong

### Preserve before repair

Pause the affected action or use its real cancellation path. Do not kill unrelated sessions. Save the initial conditions, current revisions, actor/tool inputs, observed outputs and last confirmed effect. Classify whether effects are absent, confirmed or uncertain before retrying. Retain the original failed episode even when repair is easy.

### Locate the failure

Ask, in order only as needed:

1. Could the actor discover the correct World/root/Project and requested subject?
2. Was the relevant source allowed, current, sufficiently detailed and actually supplied?
3. Did an available description correctly trigger the fitting practice, or did wording/context misroute it?
4. Was the selected Skill/set actually present at the harness entry and loaded for this act?
5. Did the actor invoke the real native operation with the right subject, revision, scope and parameters?
6. Did credentials, authority, provider, material placement or connectivity prevent or alter execution?
7. Did the effect occur but disappear from the user's view, destination, context or later session?
8. Is the expected result/observer/test setup itself wrong or too narrow?

Bind the finding to **story + step + native capability + practice/context basis + actual evidence**. Use a plain description such as “the instruction was updated on disk, but the new agent could not discover it” before the technical detail. A model's self-report is evidence of its report, not automatically the cause.

### Repair at the right level

A misleading Skill trigger is a procedure/interface repair, not necessarily a missing API. A wrong context scope is a resolver/source-policy issue. A unavailable provider is not fixed by editing a test to return success. A lost task/receipt boundary is fixed in the native caller/receiver, not by a new campaign ledger. A wrong expectation is corrected with source-backed explanation; an unresolved product decision goes to the person once, clearly.

The orchestrator may allocate a bounded repair to the relevant owner and integrate it through the current branch/review/check discipline. It may use Factory if operationally available and appropriate, but needing Factory to build the ability to test Factory would be circular. The approved local/native/GitHub procedure remains an explicit bootstrap path. No recursive unlimited delegation or retry is implied.

### Repeat fairly

After repair, establish the new source/build/installed/running/practice basis. Restore comparable input from a safe baseline and rerun through the normal entry with a fresh agent where context/learning could contaminate the result. If the actor was coached, label that attempt assisted and repeat unassisted. A repaired continuation can succeed while the original failure remains recorded. Never delete the failing assertion or downgrade an unmet parent requirement to pass.

## 8. How the person enters the campaign

After prerequisites have been established, present one useful first activity, not an installation lecture. For example:

> Open your usual coding tool in this existing project and ask it to fix the selected bug. You should not need to paste your project instructions. We'll check that it finds the right source, runs the right checks and keeps your unrelated edits intact.

Later offer the deeper prepared activities: create a research assistant; change its instructions; explore a real decision in the graph; reconsider changed evidence; run work on the spare machine; compare two actual solutions; share a bounded collection; inspect a clear completed result; recover from an approved interruption.

The person should be asked about interpretation, useful choices, clarity and whether they can keep working. They should not supply a fake approval to unblock every routine test or discover preventable hidden setup steps on behalf of the operator.
