## The developer's ordinary world

I can have several kinds of work in progress and understand them without turning them into the same kind of thing. I can work directly with an agent in a terminal, commission a coordinated development task, leave an unrelated native agent running, and contact a persistent assistant from another device. I can move my attention between them without recreating their work. When something breaks, I can find what needs repair and return to the task.

**Work is the human activity; Factory is its commissioned developmental modality.** AIKit supplies operative resolution, SessionSpace and native environment/surface bindings. Actuation owns realised agency and authority. Workcell observes and supplies material worlds, including processes not launched by Factory. A terminal pane, provider session, semantic Agent, source Project and Factory Run remain distinct related objects.

The distinctions are operational, not a mandatory stack. A bare terminal with an existing harness is a valid world. A remote Workcell is not another tab. Capabilities differ by actual provider and version.

## GW — Contact the same situated assistant through a real gateway

Source: **O:I #154**, particularly connector SDK, C Telegram, D ecology, E Workcell/Fabric, F Cradle/Factory and its physical remainder. Telegram is already the first full acceptance connector. The product promise is not merely that an incoming message can be journalled.

The meaningful complete route is **real authorised Telegram sender → connector identity and conversation mapping → gateway admission → actual resident agent with the right context → useful permitted operation → observed result → attributed reply visible to that sender → later continuation through another supported Surface**. Preserve each distinct admission boundary. A bot label is not the sender's authority; an ACK is not agent work; a provider message ID is not canonical AgentSession identity.

### Telegram is a real acceptance route, not a demand to install a new chat integration here

Preparation uses approved disposable content, an explicitly selected bot/account/conversation and a finite spend/time budget. Credentials stay on the authorised machine. Record current platform API and native adapter versions, permitted egress and retention/redaction. Use polling and/or webhook as actually supported; neither is inferred from the other's fixture. Additional connector platforms retain #154's breadth obligations and platform-specific capabilities without being falsely certified by Telegram.

For proof distinguish deterministic fake-Bot-API tests; actual connector/network tests; actual resident-model/native-effect tests; actual receiving-device interaction; and the person's assessment. A blocked real-token leg remains blocked, not passed by the fake API. Do not send unsolicited messages to a real group to obtain evidence.

## One coherent scenario joining these stories

In an approved disposable world, undertake a real Factory change in Herdr while a direct tmux task and an unrelated native harness remain active. Open the relevant source/knowledge graph elsewhere, ask the same persistent assistant about progress from Telegram, let it consult a second real agent, and inspect the actual artifact and checks. Interrupt one selected gateway or provider boundary, recover within bounds, and return the resulting discrepancy through the document/capability/practice relations. Repeat the affected task with a fresh actor.

This is an integrated **episode**, not a replacement for the complete source scope. Its success does not certify every SDK or host. Run the minimum, platform-specific and individual-native-operation cases separately, then this composite. The person supplies genuine choices and experiential return; the local lead handles technical orchestration.
