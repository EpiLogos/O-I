# {O:I} Product Surfaces

{O:I} is easiest to enter by need rather than by repository name.

The six surfaces are centres of responsibility, not mandatory stages in one runtime pipeline. A person can use only the surfaces they need, and each product remains independently useful outside {O:I}.

The composition descriptor records only the sparse facts O:I needs to identify, register, disclose, snapshot, and verify a surface. Native repositories remain authoritative for product behaviour, configuration, and product-specific acceptance.

## Persistent personal ground — Central

A useful agentic system needs somewhere durable to stand. Central gives the user a personal working ground for human-authored Control, ordinary Work, machine intent, recovery, and the stable Actions/Connectors that operate those concerns.

The native command is `ctrl`; in a composed installation the transparent alias is `oi ctrl ...`.

Central publishes the Cargo source-install contract needed by composition: install `ctrl` from its Rust package, initialize the native root, and inspect it through structured doctor and Action listing. O:I can register an already compatible `ctrl` or follow that exact native contract at its pinned tested revision. It never copies Central configuration into O:I state.

Central also currently publishes the first directly invokable native verification contract used by `oi verify`: native `central.doctor`. O:I preserves the native operation's result and evidence rather than defining a separate Central health model.

## Agent actuation — Actuation

Actuation is the developmental and reference home for first-class agentic actuation: agent and harness contracts, model/harness/agent-instance research, and reusable experimental/runtime material for how agency is constituted and operated.

The QL agent-runtime experiments that historically lived in `agent-system-design` now belong canonically to this Actuation line. Software Factory remains the developmental-system surface; O:I does not preserve the old ownership assumption merely because historical experiment material is still visible in that repository.

Actuation is currently a repository/reference workbench rather than a released native CLI, so O:I assigns no command alias. Its live `main` does not yet publish a stable O:I-invokable native self-check; `oi verify` reports that state as `unsupported` instead of importing Actuation research semantics or executing branch-only experiments as acceptance.

## Capability and context resolution — AIKit

AIKit owns capability, context, model, profile, Skill/tool, HarnessComposition, session, and Surface resolution. The native command is `aikit`, exposed transparently as `oi kit ...` when installed.

AIKit V2 development and product-completion work remains native AIKit work. Until the accepted native main publishes the self-check contract intended for suite convergence, O:I reports its native verification declaration truthfully rather than treating command presence or a feature branch as acceptance.

## Developmental agency — Software Factory

Software Factory owns developmental Project, Run, evidence, candidate, repair, and ExecutionDisposition semantics. Its canonical repository remains `EpiLogos/agent-system-design`.

The current native `main` is still the canonical Factory corpus/base while implementation work advances on its own reviewable lines. The later six-repository harmonisation pass will decide the accepted foundational mainline candidate. O:I therefore registers an exact source checkout when useful and does not invent a Factory CLI, copy Run semantics, or execute historic QL-runtime experiments as Factory verification.

## Material execution — Workcell

Workcell owns material execution: processes, services, storage, network/fabric, provider relationships, placement, and lifecycle. O:I can register the exact selected native source and later invoke the deterministic self-check Workcell publishes for the harmonised candidate.

Physical reference-machine and fabric/provider acceptance remain Workcell-owned. The Suite Snapshot and Composition Receipt can identify those outstanding requirements and later attach their native evidence; O:I does not choose a provider or turn a particular fabric such as Tailscale into O:I semantic identity.

## Recursive formal intelligence — Quaternal Logic

**Quaternal Logic** is the public name for the formal QL/MEF system implemented in `EpiLogos/QL-MEF`: operators, refraction, kernel/service work, and structural research surfaces.

O:I keeps only composition-level identity, exact revision, docs/Skill discovery, and the declared native verification seam. Formal QL/MEF verification remains in QL-MEF.

An alias appears only when a product actually exposes a native CLI. A verification operation appears only when the owning product publishes a stable operation that O:I can invoke without reproducing its logic.

## Suite Snapshot and Composition Receipt

A Suite Snapshot can contain a partial composition or a later full six-surface candidate. For each selected surface it keeps only composition-level facts: product/repository identity, exact selected revision, install/register form, native entry, alias, docs, Skill, native verification declaration, accepted compatibility facts, and explicit physical/provider requirements.

A snapshot becomes `full-mainline` only when all six intended surfaces are selected and each exact revision has been explicitly accepted as the native mainline candidate. O:I does not infer that status from branch names, command reachability, or green local checks.

`oi verify` compares the current composition with that snapshot and can return distinct states including `unavailable`, `unsupported`, `skipped_physical_gated`, `failed`, `incompatible`, and `passed`. A Composition Receipt preserves the exact native operation/evidence O:I observed and leaves product-specific interpretation with the owning repository.
