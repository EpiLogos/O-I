# O:I Development Field Protocol — Current Execution Wayfinder

**Status:** design commitment (sections 0–11). The eight-session execution topology, its per-session restrictions and the S7 acceptance conditions that followed section 11 belonged to #97 (closed 2026-08-24) and were removed on 2026-09-11; the working discipline is the adopted agent-operations statement in Central, CI is `docs/CI.md`.  
**Deferred aperture:** deeper QL/intelligence interaction grammar, Wiki cognition/retrieval scripting, and Agent Development-Field Skills/Methods are intentionally left to the next intelligence specification rather than guessed here.

---

## 0. Destination

Make software development inside O:I one addressable, inspectable and executable field in which authored meaning, intended experience, capabilities, plans, code, CI, package state, material execution and returned evidence remain related without collapsing native ownership.

The whole developmental relation is:

```text
AUTHORED WORLD / PROJECT SELF-DESCRIPTION
        ↓
UX — intended experience
        ↓
CAPABILITIES
        ↓
PLAN / COMMISSION / INTENDED DIFFERENCE
        ↓
FACTORY DEVELOPMENTAL CONTINUITY
        ↓
AIKIT OPERATIVE RESOLUTION
        ↓
WORKCELL MATERIAL DEVELOPMENT WORLD
        ↓
ACTUATION / ACTUAL AGENCY
        ↓
IMPLEMENTATION + PR
        ↓
D / C / P / M EVIDENCE
        ↓
EX — actual human experience
        ↓
RETURN / RECOGNITION
        ↺
AUTHORED WORLD RENEWED WHERE WARRANTED
```

The Development Field is not another project-management database. It composes systems already present:

- **Central** — durable authored/source World and machine intent;
- **Actuation** — actual Agency, authority, Activity and Return;
- **AIKit** — operative resource/context/Git/harness/session resolution;
- **Software Factory** — Commission, Journey, Run, Evidence, Candidate and Recognition;
- **Workcell** — material execution worlds and lifecycle;
- **Quaternal Logic** — canonical structural shapes/relations and portable shape grammar;
- **O:I** — whole-suite composition, command doorway, CI composition and installation/update field;
- GitHub issues, PRs and native product CI.

The protocol is accepted when a fresh Agent can start from one developmental reference, recover what the work means and which native powers it affects, develop the intended difference against an exact basis, return exact evidence, and leave the accepted product/world state more intelligible rather than creating another archaeology layer.

```text

    ├── self/

    │   ├── governance/
    │   └── wiki/
```


# 5. QL-shaped Development Field carriers

This tranche consumes the canonical QL grammar but does not specify the deeper intelligence operations that will act through it.

## 5.1 ShapeDefinition versus ShapeBinding

Distinguish:

```text
ShapeDefinition
    QL-owned structural meaning

ShapeBinding
    attributable binding of actual project/product objects into that structure
```

Generic binding requires equivalents of:

```text
subject_ref
shape_ref
whole_ref
basis_refs
member_bindings
relation/address_bindings
derivation_ref
operator_ref?
return_refs
standing

```

## 5.2 General object law

An addressable resource may remain an ordinary `1`, open a `0/1` whole, or carry a specific QL shape only when an actual QL definition and attributable binding exist.

Do not force every document into six positions merely because QL can read sixfolds.

## 5.3 Capability matrices

Capability matrices are relational fields over real disclosed/bound wholes, not arbitrary spreadsheets decorated with QL terminology.

General structural reading:

```text
QL-shaped whole A
        ×
QL-shaped whole B
        ↓
RelationField(A,B)
```

Valid cardinalities can emerge from constituent shapes:

```text
2×2
3×4
4×4
6×6
6×12
12×12
...
```

A 6×6 field is not automatically the canonical direct↔conjugate QL 6×6.

Partial/developed shapes remain positive wholes.

## 5.4 Wider carriers

Docs, plan records, evidence outputs, scripts, Skills/Methods and Wiki readings may later gain QL ShapeBindings through the intelligence tranche.

This execution only establishes the **carrier compatibility and owner seams** required so those later bindings do not need another migration of the Development Field protocol.

Shape binding never upgrades source standing.

# 6. Capability lifecycle

## 6.1 Native capability matrices remain owner-native

Keep `ql-capability-matrix/1` or its accepted successor.

A capability retains:

```text
id
need
operation
outcome
implementation_status
standing
source_refs
code_refs
test_refs
account_ref
relations / placements
extensions
```

The relation to UX is:

```text
UX ──requires──▶ capability
capability ──supports──▶ UX
```

Internal capabilities can support other capabilities transitively and do not need fake user stories.

## 6.2 Feature PRs do not fight over generated matrices

Normal implementation PRs declare their Development Field impact but do not regenerate large canonical matrix projections unless that PR genuinely changes authored capability meaning.

Representative PR declaration:

```yaml
oi-development:
  plan_refs:
    - plan....
  ux_refs:
    - ux....
  capability_refs:
    - cap....
  expected_proof:
    - D
    - C
```

Merge means implementation reality changed.

Merge does not mean UX was verified.

## 6.3 Serialized reconciliation

Canonical matrix/account regeneration is a **convergence/post-verification responsibility** for this execution tranche, not a parallel coding lane inside each owner session.

The reconciliation operation, when run against accepted owner mains, must:

1. read exact merged diffs;
2. read declared plan/UX/capability impact;
3. reread current owner source/code/tests/contracts;
4. update implementation facts and refs;
5. detect added/removed/superseded capabilities;
6. validate UX relations;
7. validate available QL shape bindings structurally;
8. preserve evidence standing;
9. regenerate CSV/JSON/Markdown/account projections;
10. rebuild the O:I suite catalogue;
11. emit a reconciliation receipt/PR if source-controlled projections changed.

This lane is deliberately serialized to eliminate matrix merge-conflict pressure.

# 9. Packaging and update architecture

The stale-binary problem is part of this protocol, not an operational footnote.

## 9.1 Three levels only

```text
PRODUCT REVISION / ARTIFACT
    native owner fact

SUITE CANDIDATE / CHANNEL
    coherent O:I composition

MACHINE INSTALL RECEIPT
    what one machine is actually running
```

Exact SHAs/digests/attestations remain mandatory for reproducibility but are generated into immutable receipts; they must not act as scattered hand-maintained runtime selectors.

## 9.2 Historical manifests are receipts only

Historical pre-local build records remain available as evidence and reproducibility fixtures.

They do not answer:

> what should this machine run now?

## 9.3 Suite channels

Required policy:

```text
stable
    latest ratified known-good suite

mainline
    latest remotely proven coherent set of accepted native-owner mains

source
    explicit developer-source composition/override
```

The latest independent commit/release of one product does not automatically become the current suite.

## 9.4 One active suite

O:I owns one canonical machine-level active suite receipt/root.

Conceptually:

```text
OI/
├── suites/
│   ├── <receipt-A>/bin/...
│   └── <receipt-B>/bin/...
├── current
├── previous
├── receipts/
└── channels/
```

Invariant:

```text
oi aikit ...
Desktop → oi aikit ...
TUI → oi aikit ...
Agent → oi aikit ...

all resolve the AIKit executable named by the same active suite receipt,
unless an explicit source/developer modality is active.
```

No hidden registered executable may silently override that receipt.

## 9.5 Incremental update

A new whole-suite receipt reuses unchanged immutable product artifacts and only acquires/builds changed artifacts.

Whole-suite coherence does not imply reinstalling all six products every time one advances.

## 9.6 Required O:I command surface

```text
oi suite status [--json]

oi suite update [--json]
oi suite repair [--json]
oi suite rollback [--json]
oi suite channel <stable|mainline|source>

```

Development Field whole-level commands may include:

They compose owner-native operations.

# 11. CI architecture

The realised shape is in `docs/CI.md`: `verify.yml` is the one pull-request gate, surface workflows are path-scoped, `release.yml` publishes attested artifacts from main, and every check that builds or tests a sibling repository runs weekly in `cross-product.yml`.

Of the lettered lanes originally planned here, CI-B (owner implementation CI) is each owner's own main gate; CI-C (cross-product conformance), CI-E (suite candidate resolver checks) and CI-G (installed-suite fixture) live in `cross-product.yml`; CI-D (artifact publication) is `release.yml`; CI-H (branch/material debt) is `branch-hygiene.yml`. CI-A (PR declaration validation) and CI-F (serialized matrix reconciliation) were not built and are not required by any current gate.
