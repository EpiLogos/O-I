# Expression Production Sandbox

**Standing:** corrected execution ground, 16 September 2026.  
**Owner:** Point-Cloud-Demo #6.  
**Architecture ground:** QL-MEF accepted K8–K10 Expression engine + #94/AW Ta-Onta + L5 Technē dual-reading.  

## 0. Exact office of this repository

Point-Cloud-Demo is the **isolated authoring/demo copy of the Expression engine/editor already integrated into the O:I desktop cradle**.

It is used for corpus production because it is a bounded, convenient place to craft, inspect, export and accumulate large numbers of Expressions without coupling those content runs to O:I implementation work.

It is not:

- a new product or runtime tier;
- a second Expression engine;
- a new Ta-Onta API;
- an engine-integration programme;
- a semantic owner for Bimba or Return of Zero.

The accepted K8–K10 work remains the engine architecture. O:I remains the actual desktop/runtime cradle.

## 1. Production model

Use the existing editor and engine directly: scenes, formations, pins, text/glyph/image/ASCII sources, material/physics, resonance/cymatics, colour, camera, automation, sequencing, capture, recovery, import/export and Library.

Add only the smallest helpers actually required for efficient agent/human authoring. Prefer existing model/config/import/export paths and direct browser/computer use. A helper script or thin local control surface is development tooling, not a new public service or ontology.

No worktree is required merely to generate Profiles, HTML, JSON, assets or Expression artifacts. Shared-tree/direct output is the default when target paths are disjoint; isolation is used only for genuine concurrent code conflicts.

## 2. Repository-visible corpus body

Browser/IndexedDB work remains useful, but accepted corpus outputs must also be durable files in this repository.

Keep at least two separate corpus namespaces/collections:

```text
Bimba / QL-MEF Expressions
Return-of-Zero Expressions
```

Each admitted artifact should retain, where applicable:

```text
editable Expression / Profile / Scene body
source or subject refs + revision
corpus / family / branch identity
cover or useful capture
used glyph/image/ASCII/media refs
provenance / rights where external material is admitted
production/review evidence where useful
```

Exact directory names may follow the existing export/build conventions; do not introduce another authoring schema merely to store the corpus.

## 3. Forms arise from content

There is no pre-production asset catalogue.

```text
actual content need
→ find / make / adapt form
→ use it in a real Expression
→ inspect / compare
→ retain, revise or reject
→ index useful occurrences for later reuse
```

The resulting visual bank is an occurrence/provenance index over forms actually used. A recurring image, glyph or colour remains presentation/craft evidence unless its semantic relation is source-backed.

## 4. Relation to M and M′

QL-MEF owns M/Bimba and the M→M′ instrument relation. This repository does not reinterpret that architecture.

## 6. Shared-code boundary

QL-MEF and Antykathera production sessions may write artifacts into their dedicated output namespaces here.

They do **not** independently fork or modify shared engine/editor code to satisfy one corpus lane. Common authoring defects or reusable improvements return to Point-Cloud #6 and are repaired once.

## 7. Acceptance

The production sandbox is ready when:

1. the existing editor remains a stable isolated authoring surface for the same engine used by O:I;
2. Bimba and Return-of-Zero sessions can create/edit/export real Expressions efficiently;
3. durable outputs accrue in distinct source-bound collections;
4. useful form occurrences and provenance can be recovered;
5. common editor/engine defects have one repair route;
6. material/craft evidence can return to the existing Ta-Onta learning path;
7. no new runtime/integration architecture is required to make the corpus.
