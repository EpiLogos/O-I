## The four laws (bind every lane, every subagent)

1. **Port law — port, never recreate.** Before writing any new module, name
   the legacy source it ports by path:line (cradle, expressions-app, kernel,
   Archetypal-Earth). Real refactor = port + retire in the same change; no
   dual maintenance, no flag-kept corpses, no parallel stores. Native owners
   are never reimplemented; the shell binds, projects and admits.
2. **Aperture law — native actions adherence.** Every device and action uses
   declared owner operations: the action names its exact `boundary_op`
   (kernelOp / frame host-command / device change kind, as in the port
   ledger); custody and receipts stay intact; a successful UI flag is never
   evidence of a native effect.
3. **Widget law — guides, not ceilings.** The mockups are the guides
   (`wayfinder/WIDGET-GUIDE.md`, from C3): they give each device its
   shared vocabulary — states (folded/compact/configure/deep/pop-out-
   ready), knob/slider/light semantics, tooltips, keyboard, empty and
   refusing states — and the waiting component forms capabilities plug
   into. The delivered feature is expected to function and look BETTER
   than the mockup drew it; record every improvement back into the guide.
   Falling short of the guide is the only failure; exceeding it is the
   expectation.
4. **Honesty boundaries.** No audio, device-editing or performance claims
   before those owners land; Factory and Central entry points admitted only
   through their owners' manifests; all 126 targets stay pending until each
   target's stated behavior is exercised (source checks never promote a
   target); UI acceptance is by direct computer use, never from code
   reading or browser automation alone.

## The verification loop — matrices and spine inside it

Verification per lane is four things, always: (1) the lane's own checks
(typecheck, build, native tests — existing green checks are baselines, not
acceptance); (2) computer-use exercise of what the lane landed; (3) **UX
spine conformance** — the landed UI still composes through the tripartite
spine (mode × world-context × kernel epoch) with no second selection model
(`WORLD-SHELL-DESIGN.md` §2); (4) **capability matrices updated** — every
lane that changes what a product can do updates the affected matrix cells as
part of landing, using the "Situate the concern before asking" step of the
`capability-matrices` skill. Matrices change a lot to match the UI
components directly and clearly — that is the point: they are verification
evidence, not afterthoughts.
