## 0. Undertaking and first delivery

Complete the existing Flow so one human and several actual agents can converse, branch, converge and retain useful work in one NOW, then perform the same activity across Workcells and independently grounded worlds. A Flow stays rich, portable source; native journals carry contact/runtime effects; different participants keep their own sessions and contexts.

The first installed delivery is a real passage-to-explanation/Expression inquiry:

1. Open a real source and continuing Flow; bring two distinct agents into the concern.
2. Request complementary work: recover the argument and test an example. Both return independently with their sources and actual identities.
3. Develop a side inquiry and one contribution that relates both answers. Change a material assumption while an answer is still running.
4. Close the Flow/UI before the delayed response arrives. Reopen and find every response on its correct request and basis, once.
5. Continue with a fresh body across a civil Day boundary; use the retained result on a different example.
6. Repeat across Mac/Omarchy, then admit a second independently authorised person/test identity and their agent through SharedField. Keep private neighbouring source out of its actual delivered context.

The first local episode may proceed before the remote/connector work. It is an early useful increment, not closure of the whole scope.

### 6.1 Form — successor version and representation (PF1, implemented in O-I)

- **Version:** `ql-dialogue-flow v0.4`; `meta.format = {version: 4, minReader: 4}`. A writer that does not know version 4 must treat the document as read-only; this writer refuses a newer version and refuses to append to a legacy form until it is explicitly upgraded.
- **Participants** (`meta.participants[]`): `key` (stable, document-local, independent of initial and name), `binding {owner, ref?, basis}`, `role` (contributor | observer), `joined`/`left {at, revision}`, `historyFrom` (readable-history horizon). Two participants may share an initial.
- **Entries:** `authorKey`, `attribution {basis: verified|declared|inferred|unknown|imported, agency?, session?, generation?, workcell?, onBehalfOf?}`, `addressees[]`, `audience` (`"group"` or `{keys}`), `intent`, typed `relations[]` (`reply`, `branch`, `converge` ≥2, `correct`, `source`, `artifact`; each carries the target entry and the revision it was read at), `request {ref, digest}`, `basisRevision`. `replyTo` is kept as the mirror of the single `reply` relation so earlier readers still read the thread.
- **Upgrade:** explicit, deterministic, idempotent, identity-preserving. The original basis is retained as a digest of the pre-upgrade island. An initial that two participants share stays unassigned (`attribution.basis: "unknown"`); it is never resolved to the agent presently attached. Reading never mutates.
- **One validator/authoring path:** `desktop/cradle/src/flow/plural.ts` is the only implementation. The standalone form embeds it (`documents/embed-plural.mjs`; `--check` fails on drift), the app imports it, and native owners implement the same rules against the shared conformance cases in `documents/fixtures/plural-flow-cases.json` (30 cases, independent of any implementation). `npm run test:plural-flow` runs the drift gate, the cases, the app-side instance path and the standalone form in a real browser.

### 6.2 Native append and caller identity (PF1/PF2 owner: Central)

- **Owner:** Central. `central.files.write` already owns ordinary-file CAS under `Control/user/flows/` (lock, journal, `central.file-mutation/v1`, conflict as data). The append operation is its neighbour in `file_mutation.rs`, not a new registry: it rereads the current document, applies the `appendContribution` rules, and writes through the same CAS. Central's existing `central.document.mutate` has the right idempotency shape but serves `central.contribution-document/v1` JSON, not the HTML Flow instance, so it is the pattern, not the route.
- **Idempotency record:** the document itself. `entry.request = {ref, digest}` (digest = SHA-256 of the canonical request excluding id and time). Same ref and digest → recovered, no second entry, no revision change; same ref and a different payload, target or basis → refused. No separate store.
- **Caller identity:** taken from the native caller (human ref, or agent session/agent ref supplied by the owner that admitted the call), never from the request body. A body-claimed author or `attribution: verified` is not authority: an agent cannot author as a person, a verified binding refuses another agent, a human cannot produce verified agent attribution, observers and departed participants cannot contribute. The desktop today hard-codes `actor:"oi-desktop-user"`; identifying the human requires no new credential (`central.files.write` takes none), but `verified` for an agent requires the session ref AIKit supplies.
- **Finding — Flow↔NOW/Day relation gap:** after the Flow registry retirement (#177) a Flow under `Control/user/flows/` has no NOW or Day relation. Carry it through receiving (`central.receiving.submit` with `now_ref`/`day_ref`, which needs the native token) or add the relation at Central; decided at PF4 when the Day continuation is built.

### 6.3 Request, turn and output identity (PF2 owner: AIKit)

What exists: durable per-session delivery rows (`encounter_deliveries`, phases queued→dispatching→submitted→uncertain→returned/failed/cancelled), caller-supplied `delivery_ref` with conflict refusal, per-connection-generation attribution of journaled provider events, one active delivery per session (`encounter.delivery_pending`), an owner-written journal that outlives any UI client, `SendGroup` over explicit sessions.

What is missing, and is built here:
1. **No provider turn or output identity.** ACP (claude, codex, hermes), Pi-RPC and Prime-RPC surface none. Decision: **serialize per session** (the existing one-active-delivery rule is the provider-independent correlation) and record the delivery→first/terminal cursor mapping as the output identity. Concurrency across independent sessions is unchanged. No adapter infers an answer from the newest assistant block.
2. **No durable request entity** spanning recipients. Add a native conversation request record: entry/revision basis, author, target policy, the roster revision the recipients were resolved against, and one delivery per recipient with its own state and its own contribution reference.
3. **Nothing native consumes a `returned` delivery.** Add the reply reducer (text between `first_cursor` and `terminal_cursor` carrying the `delivery_ref`) and an incorporation step owned by the encounter owner, not React: on terminal state it calls the Central append with the recipient's verified caller identity and the deterministic operation ref, records inclusion, and reconciles on owner open/reconnect. UI closure is an observer leaving.
4. **Crash recovery.** An owner crash leaves `dispatching`/`submitted`/`uncertain` rows until an operator reconciliation, which records `reconciled-no-replay`. The conversation request reconciles each recipient from its journal and never blindly replays an unknown external dispatch.

### 6.4 Remaining bindings

- **Shared Flow source/write owner:** first delivery — the existing ordinary file under Central on the owning machine is the write authority; remote contributions arrive through the authorised native route; the SharedField adapter records participation and the Contribution projection, never a competing writable document.
- **Addressed / facilitated / team:** addressed is the default (only named recipients receive one admitted act); facilitated means the selected participant composes and delegates bounded contributions; team means an explicitly chosen AgentSet with turn/time/tool budget and stop/wait conditions carried through relays. All use the existing AIKit dispatcher and Routine machinery; AIKit's `SendGroup` takes explicit sessions today, so AgentSet/profile expansion at an exact roster revision is part of PF2/PF3.
- **Baseline to preserve:** the one-to-one path is `FlowSurface.tsx` — one `answerWith` binding in React state and localStorage, one `awaitingAnswer` ref, one `seenBaseline`, and the answer is whichever newer assistant block the watcher sees. Source-read failures: a second recipient cannot be bound; closing the view loses the pending answer; two concurrent replies cannot be told apart. These are source readings; the same activity is executed against the real encounter owner with actual sessions as the first replay, before and after PF2.
