## Proposed presentation-state contract for review

This is a recommendation, not an amendment to D19. Sidebar modes are keyed by ProjectRef **within the workspace**, harmonizing with the companion review; a different workspace may retain a different mode for the same project:

- **Workspace:** name, pane tree, tab bindings, active pane/binding, side depths/widths, drawer state, restore requests for project/session. Autosave and schema version belong here.
- **Per-project sidebar:** selected mode (default chats/tasks), expansion/filter/scroll. Shared by tabs in that project; switching tabs does not reset it.
- **Per-surface:** subject binding, graph scope/camera, source scroll/draft, encounter draft and internal plane. Duplicate presentations must not create duplicate semantic objects.
- **Kernel:** authoritative current subject/world/project/session and owner-derived availability. Established by validated commands/events, never inferred from which icon looks selected.
- **Transient UI:** context menu/popover, resize interaction, keyboard focus. Full-view toggle holds a return snapshot; dismiss restores it and does not cancel work.

Decision still needed: when a tab from another project activates, should the sidebar reveal that project automatically or retain an explicitly fixed browsing scope? Recommended seed: reveal active project's row without changing its stored mode; provide explicit scope control only if a demonstrated workflow requires it. Avoid introducing a “lock sidebar” option speculatively.
