   dist, build output and running native app with the active developer; package
   visual tests are independent and do not certify native bootstrap.

## Rolling development and reproducible evidence

Use two separate concepts:

- **Development selection:** current mainline of each native product, or an
  explicitly identified candidate being developed for the current increment.
  Fresh upstream work should become available through normal sync/build/install,
  without a human-maintained revision ceiling in suite/mainline.json.
- **Verified composition:** an automatically recorded exact set of commits,
  artifact identities, native dependency locks/contracts and test receipts for
  one gate/release. It remains reproducible even after mains advance.

Select a stable candidate for a build/test operation; don't change binaries
under a running session or change dist while its tests execute. Refresh changed
products at development boundaries. A newer version can expand capabilities and
still change an interface, so native tests plus affected-consumer integration
are the condition for promotion, not age or 'main' alone. Keep a known-good
artifact for rollback and report a failed update explicitly.

Existing code to extend, not duplicate:
`cli/src/frontdoor.rs`, `suite_v2.rs` (dev sync/build/test),
`current_main_install.rs`, `trust_closure.rs`, `status.rs`, `verification.rs`.
The current sync path preserves dirty/diverged work but follows configured
upstream; verify actual branch/source before interpreting that as product main.
The descriptor-based install path has its own readiness checks. Consolidate
policy through the current seams rather than adding a second resolver.

Retain Cargo/JS dependency locks. The proposed change removes the suite snapshot
as a development ceiling; it does not remove reproducibility, provenance,
version negotiation, source integration declarations, or truthful drift checks.
Distinguish an available newer source, the currently running binary and the last
verified release. They are different facts, not automatically errors.

## How an O-I requirement propagates into products

1. Name the native owner and missing operation/read model/contribution.
2. Implement it in that product, with its contracts/tests and compatibility
   treatment. Use an explicit development candidate to prove the O-I seam before
   promotion; never masquerade as already accepted main.
3. Land according to that repo's conventions. Rebuild/install the changed owner
   through its descriptor; refresh its contribution and the affected consumer.
4. Run owner tests and cross-product acceptance. Capture the resolved composition
   automatically. CI should repeat affected-consumer checks on native main changes
   using the same declared dependencies, not a second manually maintained graph.
5. Publish the capability through the existing Action/Surface/contribution seam.
   A compatible new Action can appear through owner disclosure; a genuinely new
   interaction may still require an intentional O-I presentation. Do not promise
   that every product feature can generate its own finished UX automatically.

Product improvements must benefit CLI/agent/other consumers, not live only in
an O-I shim. Central keeps durable authored source; AIKit keeps resolution,
knowledge/familiarity and body/Surface composition; Actuation keeps agency and
execution/activity; Factory keeps developmental work; Workcell keeps material
placement; QL keeps its instruments.
